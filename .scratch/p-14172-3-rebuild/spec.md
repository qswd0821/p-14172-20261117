# p-14172-3: 56강까지 프로젝트 재구축 (글·댓글 CRUD REST API를 TDD로)

Status: done (2026-11-18, 태그 001~026)

## Problem Statement

강의(slog.gg/p/14172) 1부(1~32강, REST API)와 2부(33~56강, REST API by TDD)를 처음부터 다시 따라 만들며 복습하고 싶다. 강의 원문에는 강의별 설명과 강사 커밋 링크만 있고 코드는 거의 없어서, 원문만으로는 강의와 같은 결과물을 재현하기 어렵다. 강사 리포는 강의 단위로 커밋이 100개 가까이 있어서, 나중에 다시 볼 때 기능 변화 흐름을 따라가기 힘들다.

## Solution

빈 Spring Boot 프로젝트(`p-14172-3`)에서 시작해 강사 리포의 강의별 태그 diff를 기준으로 56강까지 다시 구현한다. 결과는 새 GitHub 리포 `qswd0821/p-14172-3`(public)에 기능 변화 단위로 묶은 26개 커밋으로 남기고, 커밋마다 순서 태그(`001`~`026`)를 붙여 순서대로 넘겨 볼 수 있게 한다. 최종 결과물은 글과 댓글의 CRUD(다건조회, 단건조회, 작성, 수정, 삭제) REST API이고, 2부에서 MockMvc 통합 테스트로 이를 검증하며 마지막 댓글 작성은 TDD로 구현한다.

진행은 한 커밋씩 한다. 구현하고, 동작을 확인한 결과와 변경 사항을 사용자에게 보여 주고, 사용자가 "커밋해"라고 하면 그때 커밋하고 태그와 함께 바로 push한다.

## User Stories

1. 학습자로서, 1~3강의 프로젝트 세팅(의존성, 엔티티, 샘플 데이터)이 한 커밋으로 묶이기를 원한다. 그래야 시작점을 한 번에 볼 수 있다.
2. 학습자로서, 앱을 실행하면 개발용 H2 파일 DB에 글 3개와 댓글들이 샘플 데이터로 만들어지기를 원한다. 그래야 바로 API를 호출해 볼 수 있다.
3. 학습자로서, H2 콘솔로 개발 DB를 들여다볼 수 있기를 원한다. 그래야 데이터 상태를 확인할 수 있다.
4. 프론트엔드 개발자로서, 글 다건조회 API로 모든 글 목록을 JSON으로 받기를 원한다. 그래야 목록 화면을 그릴 수 있다.
5. 프론트엔드 개발자로서, 글 단건조회 API로 특정 글 하나를 JSON으로 받기를 원한다. 그래야 상세 화면을 그릴 수 있다.
6. 프론트엔드 개발자로서, 응답에 엔티티가 그대로 노출되지 않고 DTO로 정해진 필드만 오기를 원한다. 그래야 백엔드 내부가 바뀌어도 API 계약이 유지된다.
7. 백엔드 개발자로서, 글과 댓글의 양방향 관계 때문에 JSON 직렬화가 무한 루프에 빠지지 않기를 원한다.
8. 프론트엔드 개발자로서, 특정 글의 댓글 다건조회와 단건조회 API가 있기를 원한다. 그래야 글 상세 화면에 댓글을 보여 줄 수 있다.
9. 프론트엔드 개발자로서, 댓글을 삭제할 수 있기를 원한다.
10. 프론트엔드 개발자로서, 글을 삭제하면 그 글의 댓글도 함께 삭제되기를 원한다.
11. 프론트엔드 개발자로서, 조회가 아닌 요청의 응답에 `resultCode`, `msg`, `data`가 공통 형식(RsData)으로 오기를 원한다. 그래야 성공·실패 처리를 한 방식으로 할 수 있다.
12. 프론트엔드 개발자로서, 응답에 데이터가 없을 때는 `data`가 명시적으로 비어 있기를 원한다.
13. API 사용자로서, 삭제가 GET이 아니라 DELETE 메서드로 호출되기를 원한다. 그래야 HTTP 의미에 맞는다.
14. 프론트엔드 개발자로서, JSON 본문(제목, 내용)으로 글을 작성할 수 있기를 원한다.
15. 프론트엔드 개발자로서, 글을 작성하면 만들어진 글 정보를 응답으로 받기를 원한다.
16. 프론트엔드 개발자로서, 응답의 `resultCode`(예: `201-1`)에 맞는 HTTP 상태코드가 실제로 오기를 원한다. 그래야 상태코드만 보고도 결과를 판단할 수 있다.
17. 백엔드 개발자로서, 액션 메서드마다 `ResponseEntity`를 쓰지 않고 공통 후처리(ResponseAspect)로 상태코드를 맞추기를 원한다. 그래야 코드가 단순해진다.
18. 프론트엔드 개발자로서, JSON 본문으로 글을 수정할 수 있기를 원한다.
19. 프론트엔드 개발자로서, JSON 본문으로 댓글을 수정할 수 있기를 원한다.
20. 백엔드 개발자로서, 테스트가 개발 DB가 아닌 메모리 DB에서 돌고 케이스마다 롤백되기를 원한다. 그래야 테스트끼리 서로 영향을 주지 않는다.
21. 백엔드 개발자로서, 글 작성 API를 HTTP 요청 단위로 테스트하기를 원한다. 그래야 실제 사용과 같은 흐름이 검증된다.
22. 백엔드 개발자로서, 테스트에서 어떤 컨트롤러의 어떤 메서드가 실행됐는지 확인하기를 원한다.
23. 프론트엔드 개발자로서, 테스트가 응답 JSON의 모든 필드를 검사하기를 원한다. 그래야 필드 누락이나 이름 변경이 바로 드러난다.
24. 백엔드 개발자로서, 요구사항이 바뀌면(예: 글 작성 응답에서 totalCount 제거) 테스트를 먼저 고치고 실패를 확인한 뒤 구현을 고치기를 원한다.
25. 백엔드 개발자로서, 글 수정 테스트가 있기를 원한다.
26. 백엔드 개발자로서, 글 삭제 테스트가 있기를 원한다.
27. 백엔드 개발자로서, 글 단건조회 테스트가 있기를 원한다.
28. 백엔드 개발자로서, 글 다건조회 테스트가 글 개수까지 확인하기를 원한다.
29. 프론트엔드 개발자로서, 없는 글을 조회하면 RsData 형식의 404 응답을 받기를 원한다.
30. 백엔드 개발자로서, 예외를 전역 예외 핸들러 한 곳에서 처리하기를 원한다.
31. 프론트엔드 개발자로서, 제목 없이 글을 작성하면 어떤 필드가 왜 틀렸는지 담긴 400 응답을 받기를 원한다.
32. 프론트엔드 개발자로서, 내용 없이 글을 작성해도 400 응답을 받기를 원한다.
33. 프론트엔드 개발자로서, 잘못된 JSON 형식으로 글을 작성하면 400 응답을 받기를 원한다.
34. 백엔드 개발자로서, 댓글 단건조회와 다건조회 테스트가 있기를 원한다.
35. 백엔드 개발자로서, 댓글 삭제와 수정 테스트가 있기를 원한다.
36. 백엔드 개발자로서, 댓글 작성 기능을 테스트를 먼저 쓰고 구현하는 TDD로 만들기를 원한다.
37. 프론트엔드 개발자로서, 댓글을 작성하면 응답에 실제 DB id가 담긴 댓글 정보가 오기를 원한다(0이 아니라).
38. 학습자로서, 각 커밋 메시지만 읽어도 무엇이 바뀌었는지 알 수 있기를 원한다.
39. 학습자로서, 커밋마다 `001`, `002` 같은 태그가 있기를 원한다. 그래야 나중에 순서대로 다음 커밋으로 넘어가기 쉽다.
40. 학습자로서, 커밋 전에 테스트나 동작 확인 결과와 변경 사항을 먼저 보고, 내가 허락할 때만 커밋되기를 원한다.

## Implementation Decisions

- **기준 코드**: 강사 리포 `jhs512/p-14172-2`의 강의별 태그(`001`~`056-3`) diff를 기준으로 하고, 클래스 이름·패키지 구조·응답 형식을 강의와 같게 맞춘다.
- **기술 스택**: Spring Boot 4.1.2, Java 25 툴체인(로컬 `~/.jdks/ms-25.0.4.1`), Gradle Kotlin DSL, Lombok, Spring Data JPA, Bean Validation, H2(개발용 파일 DB `MODE=MySQL`, 테스트용 메모리 DB).
- **도메인 모델**: 글(Post)과 댓글(PostComment). 글 하나에 댓글 여러 개가 달리는 양방향 관계이고, 글이 댓글 컬렉션의 생명주기를 관리한다(orphanRemoval, cascade 삭제). 공통으로 id, 생성일, 수정일을 가진다.
- **API 계약**: 버전 접두어는 `/api/v1`.
  - 글: 다건조회, 단건조회, 작성(POST, JSON 본문), 수정(PUT, JSON 본문), 삭제(DELETE)
  - 댓글: 글 하위 리소스로 다건조회, 단건조회, 작성, 수정, 삭제
- **DTO 구분(30강 기준)**:
  - 엔티티 DTO(PostDto, PostCommentDto): record로 만들어 엔티티를 노출하지 않는다.
  - 요청 본문 DTO(…WriteReqBody, …ModifyReqBody): validation 제약을 둔다.
  - 응답 본문 DTO(…ResBody): 응답 데이터가 둘 이상일 때만 만든다.
- **RsData**: `resultCode`(형식은 "HTTP상태코드-세부코드"), `msg`, 제네릭 `data`로 구성한다. 조회 성공 응답에는 쓰지 않고, 그 외 요청과 실패 응답에 쓴다. data가 없으면 `RsData<Void>`를 쓴다. 상태코드 값 자체는 JSON에 노출하지 않는다.
- **ResponseAspect**: 액션 메서드가 RsData를 반환하면 resultCode의 앞자리로 HTTP 응답 상태코드를 맞추는 AOP 후처리다.
- **전역 예외 핸들러**: 없는 리소스(NoSuchElementException)는 404, 요청 본문 검증 실패(MethodArgumentNotValidException)는 400과 "필드-코드-메시지" 정렬 목록, 읽을 수 없는 JSON은 400. 모두 RsData 형식으로 응답한다.
- **댓글 작성 id 문제**: 작성 직후 응답에 실제 id가 담기도록 리포지터리 flush로 INSERT를 앞당긴다. flush는 커밋하지 않는다.
- **커밋 계획(26개)**:
  - 001: 1~3강 세팅
  - 002~013: 1부 기능(글·댓글 조회, DTO, 삭제, RsData, DELETE 메서드, 글 작성, ResBody, ResponseAspect, 글·댓글 수정)
  - 014~026: 2부 테스트와 TDD(테스트 환경, 글 작성·수정·삭제·조회 테스트, ResponseAspect 개선, totalCount 제거, 404, 400, 댓글 조회·삭제·수정 테스트, TDD로 댓글 작성)
- **커밋 형식**: 제목은 `NNN. 내용`(강의 범위 표기 없음)이고, 본문은 한국어 bullet로 자세히 쓴다. 같은 번호의 lightweight 태그를 붙이고, 사용자 승인 직후 커밋과 태그를 함께 push한다.
- **제외 범위**: 일부러 실패하는 중간 단계, lab 커밋, 이론 강의, POSTMAN 강의는 별도 커밋으로 만들지 않는다. 2부의 TDD 흐름은 커밋 본문에 기록한다.
- **리포 위생**: `.gitignore`에 H2 파일(`db_dev.*`)을 추가한다. IDE 파일은 기존 규칙대로 제외한다. 새 리포에는 에이전트 문서(AGENTS.md, docs/agents, GLOSSARY.md)를 넣지 않는다.

## Testing Decisions

- **좋은 테스트의 기준**: 외부에서 관찰할 수 있는 HTTP 동작만 검증하고 구현 세부는 검증하지 않는다. 각 케이스는 요청을 보내고 결과를 검증하는 두 단계로 짠다.
- **테스트 경계는 HTTP API 하나**: 컨텍스트 전체를 띄운 MockMvc 통합 테스트(테스트 프로필, 메모리 DB, 케이스별 롤백)만 쓴다. 모킹은 하지 않는다. 컨트롤러, 서비스, 리포지터리, ResponseAspect, 전역 예외 핸들러가 모두 실제로 동작한다.
- **테스트 대상**: 글 컨트롤러 테스트와 댓글 컨트롤러 테스트 두 클래스.
- **검증 항목**:
  - HTTP 상태코드, 실행된 핸들러(컨트롤러와 메서드)
  - `resultCode`, `msg`
  - 응답 JSON의 모든 필드가 있고 형식이 맞는지
  - 다건조회는 개수까지 확인한다.
  - 응답 값이 실제 DB와 맞는지 대조하는 것은 넣지 않는다(41강·43강 기준).
- **실패 시나리오는 대표 케이스만**: 없는 글 조회는 404, 제목이나 내용이 없거나 JSON이 잘못된 글 작성은 400(53강 기준).
- **사전 사례**: 이 리포에는 아직 테스트가 없다. 강사 리포의 `ApiV1PostControllerTest`, `ApiV1PostCommentControllerTest`(태그 033~056)가 기준이다.
- **1부 확인 방법**: 1부(002~013)는 테스트가 없으므로, 서버를 띄우고 curl로 해당 엔드포인트를 호출해 응답을 보여 준다. 2부(014~026)는 Gradle 전체 테스트 통과를 보여 준다.
